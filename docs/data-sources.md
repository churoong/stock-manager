## 1. DART OpenAPI (국내 재무·공시)

- **인증 방식**: 이메일 회원가입 후 인증키 발급. 개인회원은 신청 즉시 발급. 호출 시 쿼리 파라미터 `crtfc_key`로 전달
- **무료 한도**: **일일 20,000건**. 오류코드 `020`의 설명에 근거. 공식 문서가 "요청 제한이 다르게 설정될 수 있다"고 명기하므로 고정 보장값은 아니다. 오류코드 `021`은 조회 가능 회사 개수 초과로 최대 100건. 분당·초당 제한은 `[확인필요]`
- **이용 조건**: 약관 제11조 제1항에 서비스가 원칙적으로 무료라고 명시. 상업적 이용을 금지하는 조항과 데이터 재배포를 금지하는 조항은 **발견되지 않음**. 제17조의 제3자 제공 금지는 회원정보 조항이지 공시데이터가 아님. 제23조 제1항은 정확성·완전성을 보장하지 않는다고 명시
- **사용 범위**: 국내 종목 재무제표, 공시 목록, 발표일(point-in-time 스냅샷의 기준일)
- **폴백**: 캐시 → 직전 성공 스냅샷 유지 → 재무 팩터 일시 비활성화
- **출처**: `https://opendart.fss.or.kr/guide/detail.do?apiGrpCd=DS001&apiId=2019001`, `https://opendart.fss.or.kr/intro/terms.do`
- **확신도**: 공식 확인. 상업 이용 가부는 금지 조항 부존재를 확인한 것이지 명시적 허용을 확인한 것은 아님

### 호출 규격 (실제 서버 응답으로 검증)

```
GET https://opendart.fss.or.kr/api/corpCode.xml?crtfc_key=<키>
GET https://opendart.fss.or.kr/api/fnlttMultiAcnt.json?crtfc_key=<키>&corp_code=<쉼표로 이은 고유번호>&bsns_year=2025&reprt_code=11011
GET https://opendart.fss.or.kr/api/fnlttSinglAcntAll.json?crtfc_key=<키>&corp_code=<하나>&bsns_year=2025&reprt_code=11011&fs_div=CFS
```

- 인증키는 **쿼리 파라미터 `crtfc_key`** 로 보낸다
- **DART 는 종목코드가 아니라 고유번호(corp_code)로 조회한다.** 먼저 고유번호 목록을 받아 이어 붙여야 한다
- 고유번호 목록은 **zip 으로 온다.** 압축을 풀면 XML 하나가 들어 있고 약 30MB, 11만 건이다. 그중 **상장사는 약 3,990건**이다. 비상장사는 종목코드 자리가 공백이다
- 다중회사 API 는 **한 번에 100개까지** 묶을 수 있다. 실제 호출로 확인했다
- 보고서 코드: `11011` 사업, `11012` 반기, `11013` 1분기, `11014` 3분기
- 응답 상태 `000` 정상, `013` 조회된 데이터 없음

**상태 013 은 실패가 아니다.** 그 묶음에 해당 기간 데이터가 없다는 뜻이다. 실제로 상장사 100개를 묶어 보냈는데 013 이 온 적이 있었고, 원인은 그 회사들에 그해 사업보고서가 없어서였다. 묶음 크기 문제로 오해하기 쉽다.

### 시점 스냅샷의 기준: 접수번호

**`rcept_no` 앞 8자리가 접수일자다.** 이것이 "언제 알 수 있게 됐는가" 이고 백테스트가 미래를 보지 못하게 막는 기준이 된다.

| 보고서 | 접수번호 | 접수일 |
|---|---|---|
| 삼성전자 2024 사업보고서 | 20250311001085 | 2025-03-11 |
| 삼성전자 2025 사업보고서 | 20260310002820 | 2026-03-10 |

2026-03-09 에 서 있었다면 2025년 실적을 알 수 없었다. 이 경계를 무시하면 결과를 알고 투자한 성적이 나온다.

### 파싱에서 걸리는 것 세 가지

**금액 표기가 API 마다 다르다.** 다중회사 API 는 쉼표를 넣어 주고(`333,605,938,000,000`) 단일회사 API 는 넣지 않는다(`333605938000000`). 한쪽만 처리하면 값이 통째로 사라진다. 회계 표기의 괄호는 음수다.

**같은 계정이 여러 재무제표에 중복으로 나온다.** 당기순이익이 손익계산서(IS), 포괄손익계산서(CIS), 현금흐름표(CF), 자본변동표(SCE)에 모두 있다. `sj_div` 로 걸러 읽지 않으면 엉뚱한 값이 들어간다.

**회사마다 계정 이름이 다르다.** 매출은 `매출액`, `수익(매출액)`, `영업수익` 이 섞여 있다. 다중회사 API 에는 `account_id`(IFRS 표준 식별자)가 없어 이름으로 맞출 수밖에 없다. 단일회사 API 에는 `ifrs-full_Revenue` 같은 식별자가 있다.

885종목을 100개씩 묶으면 기간당 9회다. 5년 20개 기간이면 180회이고 고유번호 목록 1회를 더해도 181회다. 일 20,000건 한도에 한참 못 미친다.

### 1.1 배당에 관한 사항 (alotMatter) — 2026-09-17 실제 응답으로 확인

장기 적립 종목 공개의 선행 조건이다(사용자 결정: 배당 수집·검증 뒤 공개). 어댑터 `batch/sources/dart_dividends.py`.


- 줄(`se`)마다 단위가 다르다: 총액·순이익 **백만원**, 주당값 **원**, 성향·수익률 **%**. 저장할 때 원으로 맞춘다
- `stock_knd` 가 보통주·우선주로 나뉘는 줄(주당 현금배당금, 현금배당수익률)과 `-` 인 줄(총액·성향)이 있다
- 값이 없으면 `-`. 무배당인지 해당 없음인지 구분되지 않는다 `[확인필요]`

| 확인한 응답 | 보통주 주당배당금 (당기·전기·전전기) | 현금배당금총액(백만원) |

### 1.3 분기·반기 보고서 — 금액의 기준 (2026-09-18 확인)

`jobs/financials.py` 는 기본으로 네 보고서(11011 사업·11012 반기·11013 1분기·11014 3분기)를 모두 받는다.

**손익 계정의 `thstrm_amount` 는 그 분기 3개월 값이다. 반기·3분기 보고서도 누적이 아니다.** 누적(연초부터)은
`thstrm_add_amount` 에 따로 온다. 저장하는 것은 `thstrm_amount` 이므로 DB 의 분기 손익은 모두 3개월 값이다.
재무상태표 항목(자산·자본)은 분기 말 시점값이다.

확인 (다중회사 주요계정 `fnlttMultiAcnt`, 연결, 손익계산서). 1~3분기 3개월 값을 더하면 누적과 **원 단위까지 같다**:

| 회사 · 2025 | 1분기 | + 2분기(반기 보고서 thstrm) | = 반기 누적(thstrm_add) | + 3분기 | = 3분기 누적 |
|---|---|---|---|---|---|
| 삼성전자 매출 | 79.14조 | 74.57조 | 153.71조 ✓ | 86.06조 | 239.77조 ✓ |
| 삼성전자 영업이익 | 6.69조 | 4.68조 | 11.36조 ✓ | 12.17조 | 23.53조 ✓ |
| SK하이닉스 매출 | 17.64조 | 22.23조 | 39.87조 ✓ | 24.45조 | 64.32조 ✓ |
| SK하이닉스 영업이익 | 7.44조 | 9.21조 | 16.65조 ✓ | 11.38조 | 28.04조 ✓ |

삼성전자 2026 반기도 같다(1분기 133.87조 + 2분기 171.50조 = 누적 305.37조).

**함정**: 반기 보고서 행의 `thstrm_dt` 는 "2026.01.01 ~ 2026.06.30" 처럼 **누적 기간**을 적는데, 같은 행의
`thstrm_amount` 는 4~6월 값이다. 기간 표기만 보고 누적으로 읽으면 틀린다. 1분기 행은 두 값이 같다.

- 팩터·신호·밸류에이션은 여전히 **사업보고서(11011)만** 쓴다. 분기는 종목 상세의 표시 전용이다
- 화면은 열 이름을 보고서가 아니라 분기로 적는다: "2분기(4~6월)" (예전 "반기" 는 1~6월로 읽혔다)
- 4분기 3개월 값은 사업보고서에만 있다: 연간 − 3분기 누적. 누적(`thstrm_add_amount`)을 저장하지 않아
  지금은 1~3분기 합을 빼야 한다. **화면에 싣지 않았다** — 다음 후보 (분기가 하나라도 빠지면 틀린 값이 된다)

### 1.2 공시 목록 (list.json) — 2026-09-17 붙임 (Step 27)

종목 상세의 "최근 공시" 와 장중 공시 알림의 재료. 어댑터 `batch/sources/dart_disclosures.py`, 배치 `batch/jobs/disclosures_kr.py`.

```
GET https://opendart.fss.or.kr/api/list.json?crtfc_key=<키>&corp_code=<하나>&bgn_de=YYYYMMDD&end_de=YYYYMMDD&page_count=100
```

- **확인된 필드만 쓴다**: `status` · `list[].rcept_no` · `list[].report_nm`. 장중 경로가 같은 필드를 실제로 읽고 있다(`docs/intraday.md` 2장 disclosure)
- 접수일은 **접수번호 앞 8자리**로 낸다(위 "시점 스냅샷의 기준"). `rcept_dt` 가 오면 그것도 받지만 없어도 된다
- 그 밖의 필드(`corp_code` `flr_nm` 제출인 `rm` 비고)는 있으면 쓴다 `[확인필요: 실제 응답의 키]`. `page_count` 상한 100 도 기억에 의존 `[확인필요]`

## 2. KRX 정보데이터시스템 Open API (종목 마스터·지수)

- **인증 방식**: 회원가입과 약관 동의 후 인증키 신청. **API별로 이용신청을 따로** 해야 한다. 인증키 유효기간은 제공일로부터 1년이고, 12개월 미사용 시 사전 공지 없이 삭제된다
- **무료 한도**: **키당 1일(0시~24시) 10,000회**. 초과 시 서비스 중지 가능. 하루치 전종목이 1회 호출로 오므로 여유가 크다. 10년 백필도 시장당 약 2,450회
- **이용 조건**: 공식 약관에 **"비상업적인 목적으로만 이용할 수 있습니다"**, **"제공받은 정보를 제3자에게 제공할 수 없습니다"**가 명시돼 있다. 이 앱은 인증된 단일 사용자만 접근하고 저장소도 프라이빗이라 부합한다. **화면이나 데이터를 외부에 공개하면 위반**이다
- **사용 범위**: 유가증권·코스닥 종목기본정보, 유가증권·코스닥·ETF 일별매매정보. **국내 시세의 1순위 경로.** 코넥스는 부르지 않는다. 지수 API(`idx`)는 `krx.API` 에 식별자만 있고 부르는 코드가 없다 — 지수는 야후(`^KS11`/`^KQ11`, `services/trend.py`·`jobs/index_prices.py`)다 (2026-09-29 정정, docs/infra.md 25.605)
- **일별 시세 폴백 (2026-09-28, docs/infra.md 25.505)**: 한 시장의 일별매매정보가 실패하거나 비면 일일 배치가 **그 시장의 활성 종목을 야후(`yahoo_symbol`, `.KS`/`.KQ`)로 대신 받는다.**
  - 그 거래일 봉만 넣는다. 거래대금(`value`)·등락률·수정종가는 비운다. 야후는 거래대금을 주지 않아서다 — 유니버스 20일 평균은 거래대금을 모르는 날을 분자·분모에서 뺀다(25.518).
  - `source='yfinance'` 로 남는다. **거래소가 돌아온 다음 일일 배치가 최근 10일 안의 야후 날을 거래소 값으로 다시 받는다**(`_heal_yahoo_days`, 25.513 — 백필은 평소 자동으로 돌지 않아 "백필이 덮는다" 는 맞지 않았다). 그 하루 동안은 단기 신호의 60일 거래대금 평균이 비고(신호 없음), 그날 기업행위(분할 등) 감지를 못 한다 — 리포트 경고에 적는다. 다시 받은 날의 기업행위도 그때 본다(25.518). 유니버스 20일 평균은 거래대금을 모르는 날을 0 이 아니라 빼고 낸다(25.518).
  - 거래소 값이 이미 있는 종목은 덮지 않는다(`--force` 재실행, 25.513). 호출은 시장당 약 14조각(2,700종목 ÷ 200).
  - 리포트에 "야후로 대신 받음" 경고를 싣는다. pykrx 는 data.krx.co.kr 로그인 요구로 막혀(5절) 건너뛴다.
- **주의**: 별도의 업종 분류 API가 목록에 없다. 업종은 **DART 기업개황**(`company.json`)에서 받는다(15절). 예전에 적은 "섹터 지수 경로로 우회" 는 구현되지 않았다 (2026-09-29 정정)

### 호출 규격 (실제 서버 응답으로 검증)

```
GET https://data-dbg.krx.co.kr/svc/apis/{카테고리}/{api_id}.json?basDd=YYYYMMDD
헤더: AUTH_KEY: <인증키>
```

- **데이터 도메인은 `data-dbg.krx.co.kr`다.** `openapi.krx.co.kr`은 키 신청용 포털이다. 이걸 헷갈리면 아무것도 안 된다
- 인증키는 **요청 헤더 `AUTH_KEY`**로 보낸다. http로 보내면 리다이렉트되며 헤더가 유실되므로 https를 쓴다
- 파라미터는 **`basDd` 하나뿐이다.** 종목별 조회도 기간 조회도 없다. **하루치 전종목 일괄 조회만 가능**하다. N일치가 필요하면 N번 부른다
- 응답은 `{"OutBlock_1": [...]}`이고 **모든 값이 문자열이다.** 결측은 JSON에서 빈 문자열, XML에서 하이픈이다
- 휴장일이나 아직 집계 전인 날은 오류가 아니라 **빈 배열**이 온다

쓰는 API는 다섯이다(`batch/sources/krx.py` `API`). 지수 둘(`idx/kospi_dd_trd`·`idx/kosdaq_dd_trd`)은 식별자만 있고 부르지 않는다.

| 용도 | 카테고리 | api_id |
|---|---|---|
| 유가증권 일별매매정보 | `sto` | `stk_bydd_trd` |
| 코스닥 일별매매정보 | `sto` | `ksq_bydd_trd` |
| 유가증권 종목기본정보 | `sto` | `stk_isu_base_info` |
| 코스닥 종목기본정보 | `sto` | `ksq_isu_base_info` |
| ETF 일별매매정보 | `etp` | `etf_bydd_trd` (13.1-1절) |

**함정: 같은 이름의 필드가 API마다 다른 값을 담는다.** 일별매매정보의 `ISU_CD`는 단축코드 6자리이고, 종목기본정보의 `ISU_CD`는 표준코드 12자리다. 두 API를 조인하려면 일별매매정보의 `ISU_CD`와 종목기본정보의 `ISU_SRT_CD`를 맞춰야 한다.

주요 필드는 `TDD_CLSPRC`(종가), `CMPPREVDD_PRC`(전일 대비), `FLUC_RT`(등락률), `ACC_TRDVOL`(거래량), `ACC_TRDVAL`(거래대금), `MKTCAP`(시가총액), `LIST_SHRS`(상장주식수)다.

## 4. yfinance (해외 시세·재무·환율)

- **인증 방식**: 없음. 야후 파이낸스의 비공식 내부 엔드포인트를 이용
- **무료 한도**: **공식 레이트리밋 수치가 존재하지 않는다** `[확인필요 — 공식 수치 부재]`. 과도 호출 시 `YFRateLimitError`나 HTTP 429가 발생한다. 이슈 트래커에 "약 100회 요청 후 30초 지연" 같은 보고가 있으나 메인테이너의 공식 수치는 없다. "시간당 30회" 류의 수치는 개인 실험 출처라 신뢰할 수 없다
- **이용 조건**: 라이브러리 코드는 **Apache-2.0**. 데이터는 별개다. 공식 README에 야후와 무관하다는 고지, **연구·교육 목적**, **"The Yahoo! finance API is intended for personal use only"**가 명시돼 있다. 개인용 비상업 앱은 문언상 허용 범위에 가장 가깝다. 상업화와 재배포는 부적합하다. 엔드포인트가 예고 없이 바뀔 수 있어 안정성 보장이 없다
- **야후 약관 (2026-09-17 교차 검증)**: https://legal.yahoo.com/us/en/yahoo/terms/otos/index.html 원문은 서면 허가 없이 스크래퍼 등 자동 수단으로 데이터를 모으는 것을 **목적과 관계없이 금지**한다. yfinance 의 "personal use" 문구는 야후의 허락이 아니다. **사용자 결정: 개인용으로 계속 사용한다.** 위반 소지가 있고 언제든 차단될 수 있다는 것을 알고 쓰는 것이다. 그래서 재무·시가총액은 야후가 아니라 SEC EDGAR(14절)에서 받고, 야후는 가격·ETF 프로필에만 쓴다
- **사용 범위**: 미국 시세·재무, USDKRW 환율, **국내 장중 현재가(약 20분 지연, Step 0 실측)**, 국내 일별 시세의 최종 폴백, **지수 일봉 (2026-09-17 추가)**: `^KS11` 코스피 · `^KQ11` 코스닥 · `^GSPC` S&P 500. 추세 필터(docs/signals.md 3.5)가 200일 이동평균을 낸다. 세 심볼을 한 번에 부르므로 하루 1회 호출이다. 한국거래소 지수 API 는 API 별 이용신청이 따로 필요해 보류 `[확인필요: 신청 여부]`

- **대응**: 일괄 다운로드로 종목 수를 줄이고, 호출 간 지연을 두고, 응답을 캐시한다
- **출처**: `https://github.com/ranaroussi/yfinance`

### 야후는 거래대금을 주지 않는다 (2026-09-16)

미국 일일 배치를 전종목으로 넓히면서 드러났다. 한국거래소는 일별매매정보에
**거래대금(ACC_TRDVAL)** 을 그대로 주지만, 야후의 일봉 응답에는 그 항목이 없다.
Open·High·Low·Close·Adj Close·Volume 뿐이다.

유니버스의 20일 평균 거래대금 하한을 미국에도 적용해야 하므로 **종가 × 거래량**
으로 갈음한다(`batch/sources/yfinance_src.estimate_turnover`).

- 이것은 **추정치다.** 실제 거래대금은 체결가마다 다른 가격으로 쌓이므로 종가
  하나를 곱한 값과 같을 수 없고, 장중 변동이 큰 날일수록 벌어진다
- 그래도 쓰는 이유는 유니버스 판정이 **자릿수를 가르는 일**이기 때문이다.
  하루 100만 달러와 1억 달러를 구분하는 데는 이 정밀도로 충분하다
- **거래대금 자체를 화면이나 리포트에 수치로 싣는다면 추정치임을 함께 표시한다**
- `prices.value` 에 국내는 실측, 미국은 추정이 섞여 들어간다. 구분은
  `prices.source` 로 한다 (`krx_openapi` 대 `yfinance`)

### 호출 수가 종목 수에 비례한다

한국거래소는 한 번의 호출로 시장 전종목 하루치가 온다. 야후는 그렇지 않아
심볼을 조각으로 나눠 부른다(기본 200개). ~~**조각 수가 곧 호출 수**~~ — **아니다** (docs/infra.md 25.601, 감사):
yfinance 1.x 의 `yf.download` 는 조각 안에서도 **종목마다 따로** 요청한다(200종목 한 조각 = 200요청). 상태 화면의 야후 호출 수
(`chunk_count` 로 셈)는 실제보다 약 200배 작다 [확인필요: 판마다 다를 수 있다]. 호출 수가 곧 차단 위험이다.
종목별 예외(429 포함)는 yfinance 가 삼키고 빈 표를 돌려주므로, 조각이 **통째로 비면** 막힌 것으로 보고 두 조각 잇달아 비면 멈춘다.

- 한 요청에 담을 수 있는 심볼 수의 공식 상한은 공개돼 있지 않다 `[확인필요]`
- 수천 종목을 조각으로 나눠 부르는 경우의 429 발생 여부는 **아직 운영에서
  확인되지 않았다** `[확인필요]`. Step 0 실측은 2종목 기준이다
- 창(lookback) 안의 여러 거래일이 같은 응답에 실려 오므로, 며칠치를 받아도
  호출 수는 늘지 않는다. 하루 빠진 날이 다음 실행에서 저절로 메워진다

### 지수 구성종목 목록 대신 이것을 쓰는 이유

`CLAUDE.md`의 유니버스 규칙은 **지수 편입 여부가 아니라 시총과 거래대금**이다. S&P 500 구성종목 목록을 쓰려면 위키백과를 긁거나 제3자 저장소에 의존해야 하는데, 출처마다 라이선스가 걸리고 갱신이 늦을 수 있다. 거래소가 직접 공개하는 전체 목록에 규칙을 적용하는 편이 명세에 더 맞는다.

### 파싱에서 걸리는 것 두 가지

**두 파일의 열 순서가 다르다.**

```
nasdaqlisted.txt: Symbol|Security Name|Market Category|Test Issue|Financial Status|Round Lot Size|ETF|NextShares
otherlisted.txt:  ACT Symbol|Security Name|Exchange|CQS Symbol|ETF|Round Lot Size|Test Issue|NASDAQ Symbol
```

같은 뜻의 열이 다른 자리에 있다. 위치로 읽으면 ETF를 보통주로, 보통주를 테스트 종목으로 읽는다. 이름으로 찾아야 하고, 열 이름이 바뀌면 조용히 틀린 값을 읽느니 실패하게 두었다.

**클래스 구분 기호가 야후와 다르다.** 거래소는 `BRK.B`, 야후 파이낸스는 `BRK-B`를 쓴다. 맞추지 않으면 그 종목만 조용히 빠진다.

파일 끝에 `File Creation Time` 줄이 붙는다. 종목으로 읽지 않는다.

### 4.1 실적 발표 예정일 `Ticker.calendar` (2026-09-18 실측)

찾지 못했다고 적어 둔 "발표 예정일 소스" 가 야후에 있었다. `yfinance.Ticker(심볼).calendar` 가
**국내·미국 모두** 다음 발표 예정일을 준다. 실측(2026-09-18, 로컬):

| 심볼 | Earnings Date | 함께 오는 것 |
|---|---|---|
| AAPL | 2026-10-30 | 배당 지급일·배당락일, EPS/매출 컨센서스(높음·낮음·평균) |
| LDOS | 2026-11-03 | 〃 |
| 005930.KS (삼성전자) | 2026-10-28 | 배당락일, EPS/매출 컨센서스 |
| 000660.KS (SK하이닉스) | 2026-10-27 | 〃 |

- 응답은 **dict** 이고 `Earnings Date` 는 `datetime.date` **목록**이다. 값이 하나면 확정에 가깝고,
  둘이면 야후도 아직 모르는 **구간**(예: 10/27~10/31)이다. 확정 여부를 따로 알려 주는 필드는 없다
  → 날짜 하나면 `is_confirmed = 1`, 구간이면 0 으로 적는다 (사용자 결정 2026-09-18)
- `get_earnings_dates()` 는 과거 발표일과 EPS 서프라이즈까지 25건을 주지만 **시각이 미국 동부시간**이라
  국내 종목의 날짜가 하루 밀려 보인다(삼성전자 `2026-10-28 02:00-04:00`). 예정일에는 `calendar` 를 쓴다
- 호출은 **종목당 1회**다. 유니버스 전체(약 2,715종목)를 주 1회 받는다(사용자 결정). 간격 0.3초는
  추정이라 429 가 나면 늘린다 `[확인필요: 첫 실행 실측]`. 429 가 5번 잇따르면 그만두고 다음 주에 받는다
- 이용 조건은 4절과 같다(개인 사용 한정). 컨센서스 수치는 **저장하지 않는다** — 추천 근거에 예측치를 쓰지 않는다

- **인증 방식**: BotFather에서 봇 생성 시 발급되는 토큰을 URL 경로에 포함. 별도 OAuth 없음. 무료이고 카드가 필요 없다

  - 통용되는 수치는 전역 초당 약 30건, 동일 채팅방 분당 약 20건이다. 텔레그램은 정확한 한도를 공개하지 않고 재량으로 조정한다고 밝혀 왔다
  - 초과 시 HTTP **429**와 함께 `parameters.retry_after`(초)를 반환한다. **`retry_after` 만큼 대기 후 재시도하는 구현이 유일하게 안전한 대응**이다
  - 메시지 길이는 텍스트 4,096자, 미디어 캡션 1,024자로 알려져 있다 `[확인필요]`. 초과하면 요청이 실패하므로 앱에서 분할 전송이 필요하다
- **이용 조건**: Bot API 이용 자체는 무료이고 상업적 봇도 허용되는 것으로 알려져 있다 `[확인필요]`. 개발자 약관 원문 미확인
- **대응**: 한도 수치를 신뢰하지 않고 **429의 `retry_after`를 지키는 재시도**와 **4,096자 기준 분할 전송**으로 구현한다. 이렇게 하면 실제 한도가 알려진 값과 달라도 동작한다
- **출처**: `https://core.telegram.org/bots/api`
- **확신도**: 확인 불가. 운영 전 공식 문서 확인 필요

### 13.1 한국거래소 Open API — 시세만 있다

포털의 서비스 목록(`openapi.krx.co.kr/contents/OPP/INFO/service/OPPINFO004.cmd`)에서

|---|---|---|

### 13.1-1 ETF 일별매매정보 — 승인 후 실제 응답 (2026-09-17)

사용자가 이용신청해 같은 날 승인됐다. `basDd=20260916` 으로 **1,171개**가 한 번에 왔다.

| 필드 | 뜻 | 예 (KODEX 200) |
|---|---|---|
| `ISU_CD` `ISU_NM` | 단축코드·종목명 | 069500 · KODEX 200 |
| `TDD_CLSPRC` `NAV` | 종가·순자산가치 | 괴리율을 낼 수 있다 |
| `ACC_TRDVAL` | 거래대금 (실제 값, 추정 아님) | 2,410,735,400,342 |
| `INVSTASST_NETASST_TOTAMT` | **순자산총액** | 24,715,731,480,706 |
| `IDX_IND_NM` | **기초지수 이름** | 코스피 200 |
| `OBJ_STKPRC_IDX` `FLUC_RT_IDX` | 기초지수 종가·등락률 | 추적오차를 낼 수 있다 |

같은 `코스피 200` 이다. 이름으로 걸러야 한다(이름에 "레버리지" 62개, "인버스" 41개, "2X" 10개).
합성은 이름의 "합성" 으로 보인다(99개) `[확인필요: 이름 표기가 전부인지]`.

**상장일 대신**: 3년 전 같은 날짜를 한 번 더 부르면 "3년 전에도 있었는가" 가 나온다.
`basDd=20230915` 에 766개, 그중 지금도 있는 것이 667개. 호출 1회로 운용 이력 조건을 판정한다.

### 13.3 야후 파이낸스 — 미국 ETF 는 충분하고, 국내 ETF 는 비어 있다

### 13.5 SEC N-PORT — 미국 ETF 의 **전 종목** 보유 (2026-10-06 실측)

장기 적립 ETF 를 "우리 장기 점수를 많이 담은 순" 으로도 보려면(2026-10-06 사용자 제안, docs/etf.md 11장) 상위 10개(13.3)가 아니라 전 종목이 필요하다.
펀드가 분기마다 내는 보유 공시 **NPORT-P** 가 그것이다. 확인 스크립트 `scripts/probe_etf_nport.py`(워크플로 `probe-etf-nport.yml`, 실행 37417155827)로 쟀다.
이 세션 컨테이너에서는 `data.sec.gov` 접속이 막혀 있어(프록시 거부) Actions 러너에서 돌렸다.

| 단계 | 경로 | 실측 |
|---|---|---|
| 티커 → 신고 주체·시리즈 | `www.sec.gov/files/company_tickers_mf.json` (열 cik·seriesId·classId·symbol) | 28,608행. VOO·VTI·QQQ·SCHD·IVV·VXUS 있음. **SPY 없음** — 단위형 신탁(UIT)이라 시리즈가 없다. 운영 세 번 모두 SPY·MDY·DIA 못 받음(2026-10-06) → 같은 지수 ETF 보유로 대신(docs/infra.md 25.982) |

- 한도: 키 없음, 연락처 든 User-Agent, 초당 10회(14절과 같다). 분기 1회 · ETF 수십 개면 수백 호출

### 14.4 공시 목록 (submissions 의 filings.recent) — 2026-09-18 실측 (Step 35)

업종 코드를 받으려고 이미 부르는 `submissions` 응답에 **공시 목록이 함께 온다**(응답이 큰 이유다).
같은 응답을 한 번 더 불러 종목 상세의 "최근 공시" 를 국내와 같은 `disclosures` 표에 채운다
(`batch/sources/sec_edgar.parse_filings`, `batch/jobs/disclosures_us.py`, 주 1회 `disclosures-us.yml`).

- `filings.recent` 는 **열 단위 배열**이 맞다 (2026-09-18 AAPL 실측, Actions 35290453310):
  열 16개 `acceptanceDateTime · accessionNumber · act · core_type · fileNumber · filingDate · filmNumber · form ·
  isInlineXBRL · isXBRL · isXBRLNumeric · items · primaryDocDescription · primaryDocument · reportDate · size`,
  **길이가 전부 1001 로 같다**. `accessionNumber[i]` 와 `form[i]` 가 같은 건이다.
  필요한 값(접수번호·폼·접수일 YYYY-MM-DD)이 없는 행은 버린다
- **`recent` 는 최근 1,000건까지다.** 그보다 오래된 것은 `filings.files` 의 묶음 파일에 있다
  (AAPL: `CIK0000320193-submissions-001.json`, 1,247건, 1994-01-26~2015-07-22). 화면은 최근 10건만 보여 주므로 묶음은 읽지 않는다
- 폼은 정기보고서와 주요사항 위주로 고른다(10-K·10-Q·8-K·20-F·40-F·6-K와 정정본).
  **전부 담으면 Form 4 가 목록을 덮는다** — 실측에서 AAPL 최근 1,001건 중 Form 4 가 **591건**이었다
  (8-K 103, 424B2 46, 144 45, 10-Q 33 …). 폼 종류는 34가지 `[확인필요: 더할 폼은 운영하며 판단]`
- 본문 주소는 `Archives/edgar/data/{CIK 앞 0 뺀 값}/{접수번호에서 대시 뺀 값}/{primaryDocument}` 가 맞다
  (실측에서 HTTP 200). 문서 이름이 없으면 묶음 폴더로 보낸다
- **CIK 는 표에 없다.** `company_tickers.json` 으로 야후 심볼에서 그때그때 맞춘다(`sectors.py` 와 같은 방식). 목록에 없는 심볼은 건너뛰고 경고로 남긴다
- 응답이 커서(평균 160KB, JPM 4.6MB) **지켜보는 종목만**(장중 감시 대상·관심·보유) 주 1회, 한 번에 300사까지. 초당 10회는 `SecClient` 가 지킨다

### 14.1 시점(PIT) — 반드시 지킬 것

- 모든 fact 에 `accn`(접수번호, 날짜 없음) · `form` · `filed`(날짜) · `fy` · `fp` · `start/end` 가 있다
- **`fy`·`fp` 는 fact 의 기간이 아니라 실린 공시의 연도다.** AAPL FY2024 순이익이 fy=2025 10-K 에도 실린다. 당기 fact 는 `accn` 과 기간 길이(연간 350~380일)로 고른다
- **`frame`·frames API 를 쓰지 않는다.** 가장 늦게 제출된 값에만 붙는다. MSFT FY2017 순이익 최초 21,204M(filed 2017-08-02) → 재작성 25,489M(2018-08-03). frame 은 재작성값에 붙어 있다
- **`form` 으로 거른다.** 10-K·10-K/A(분기는 10-Q·10-Q/A)만. JPM·WMT 에서 DEF 14A(위임장) fact 가 frame 을 차지했다
- 결산일은 dei 를 뺀 재무 fact 의 최대 `end` 또는 `dei:DocumentPeriodEndDate`. "accn 안의 최대 end" 는 dei 표지일이 잡혀 **틀린다**(검증에서 반박됨)
- `filed` 는 날짜뿐이고 17:30 ET 이후 접수분은 다음 영업일 배포다. `as_of` 는 **filed 다음 거래일**로 둔다(보수적)
