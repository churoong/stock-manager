## 0. 무엇에 답하나

**"배치가 조용히 멈춘 것을 어떻게 알아채나."**

클라우드 배치는 시끄럽게 죽지 않는다. GitHub Actions 예약이 밀리거나 건너뛰고
(docs/infra.md 1절), cron-job.org 작업이 꺼지고, 워크플로가 비활성화된다. 어느
경우든 **아무 일도 일어나지 않는다.** 실패 알림조차 오지 않는다. 실패는 배치가
스스로 알리지만(CLAUDE.md 스케줄과 알림), **안 도는 것은 배치가 알릴 수 없다.**

그래서 배치 밖에서 보는 눈이 하나 필요하다. 그것이 이 문서다.

| | 누가 알리나 | 무엇을 |
|---|---|---|
| 배치가 **실패** | 배치 자신 (`daily._notify_failure`) | 오류 내용과 마지막 성공 |
| 배치가 **안 돎** | **무응답 감시** (이 문서) | 기대 시각까지 성공 기록이 없음 |

---

**조용시간을 따르지 않는다** (2026-09-26 기록, docs/infra.md 25.258). 무응답·달력·DB 복귀 알림은 `quiet_hours` 를 보지 않고 **생기는 대로** 보낸다
(`cron/health`·`lib/tursoWatch`). 조용시간은 장중 알림(docs/intraday.md 3장)에만 걸린다. 지금 시각표로는 대부분 낮·저녁에 생기지만(국내 마감 08:57, 미국 개장 뒤),
달력 알림은 밤 1시에도 올 수 있다. 고장 알림을 밤에 받을지는 **사용자 결정**으로 남겼다(`docs/handoff.md`).

## 1. 감시는 웹 경로가 한다 (사용자 결정 2026-09-17)

Actions 예약으로 감시하면 **Actions 가 멈췄을 때 감시도 함께 멈춘다.** 감시 대상과
같은 곳에서 돌기 때문이다. 그래서 감시는 Vercel 경로에 두고 cron-job.org 가 1시간마다
부른다. Actions 분도 쓰지 않는다.

```
GET /api/cron/health     헤더 x-cron-secret: <CRON_SECRET>
```

장중 경로와 같은 토큰·같은 방식이다(docs/intraday.md 4장). 로그인 없이 부르는
경로라 `proxy.ts` 가 통과시키고 경로가 토큰으로 스스로를 지킨다.

**감시할 수 없는 것 하나.** cron-job.org 자체가 멈추면 감시도 안 돈다. 같은 제공자에
기대고 있어서 스스로는 못 잡는다. 대신 화면이 "마지막 감시 시각" 을 보여 주므로
사람이 눈으로 확인할 수 있다 `[확인필요: 이중화가 필요한지 — 무료 범위에서]`.

## 2. 무엇을 언제까지 기대하나

마감 시각을 절대 시각으로 적지 않는다. **그 시장의 개장 시각에서 잰다.**
개장 시각은 `market_sessions.open_utc` 에 있고 `exchange_calendars` 가 채운다.

이렇게 하면 서머타임과 임시공휴일이 저절로 맞는다. 화면·감시 코드에 시간대 계산이
하나도 없다. 그리고 **그날 세션 행이 없으면 휴장일**이라 아무것도 기대하지 않는다.

| 감시 대상 (`batch_runs.job_name`) | 시장 | 마감 | 왜 그 값인가 |
|---|---|---|---|
| `daily_kr` | KR | 개장 **+20분** (09:20 KST) | 장 시작 전 리포트가 목적이다. 08:27 예약에 실행이 3~6분. 개장 20분 뒤까지 없으면 오늘 리포트는 이미 의미를 잃었다. 알림에 "09:35 KST 예비 실행이 한 번 더 시도합니다" 를 붙인다(25.917) |
| `daily_us` | US | 개장 **+0분** | 같은 이유. 미국은 개장 1시간 전 예약이라 여유가 더 크다 |
| `sentiment` | KR | 개장 **−30분** (08:30 KST) | 감성 점수가 국내 일일 배치(08:27 시작)의 입력이다. 늦으면 그날 점수가 옛 감성으로 계산된다 |

숫자의 근거는 위 표가 전부다. 바꾸려면 이 표를 함께 고친다.

**"오늘 성공했나" 는 `trade_date` 로 판단하지 않는다.** 장 시작 전에 도는 배치라
그 값은 *직전* 거래일이다(`batch/core/calendar.decide`: "다루는 데이터는 직전 거래일").
오늘 날짜와 견주면 **성공한 날에도 매일 무응답 알림이 간다.** 대신 **끝난 시각**이
개장 12시간 전 이후인지 본다(`SUCCESS_WINDOW_HOURS`). 12시간이면 국내(개장 33분 전
시작)·미국(1시간 전)·감성(80분 전)을 모두 덮고 전날 실행(약 24시간 전)과는 겹치지 않는다.
**그리고 그 시장의 오늘 날짜에 끝났어야 한다**(2026-09-27, docs/infra.md 25.376). 창의 시작이 국내는 전날 21:00 KST
라, 전날 밤 손으로 다시 돌린 성공이 다음 날 성공으로 세졌다. 예약 배치는 모두 현지 자정 뒤라 정상 실행에는 영향이 없다.

### 2.0 무엇을 "돌았다" 로 치나

`success` 와 **`partial`** 이다. 이 감시가 묻는 것은 *아무 일도 없었는가* 이지 완벽했는가가
아니다. 운영에서 국내 일일 배치가 경고를 안고 `partial` 로 끝나면서 리포트는 정상 발송한
날이 있었다(2026-09-17 08:44 KST). 그날 "무응답" 을 보내면 거짓 알림이다.

세지 않는 것과 이유:

| 상태 | 왜 |
|---|---|
| `failed` | 배치가 스스로 실패 알림을 보낸다. 그리고 리포트는 나가지 않았다 |
| `skipped` | 휴장이거나 너무 늦어 건너뛴 것. 리포트가 없으니 알릴 값어치가 있다 |
| `dryrun` | 손으로 돌린 시험. 발송하지 않는다 |
| `running` | 아직 안 끝났다. 오래 굳어 있으면 화면이 "멈춘 듯" 으로 표시한다(`STUCK_AFTER_HOURS`) |

### 2.1 달력이 끊긴 경우

`market_sessions` 는 일일 배치가 채운다. 배치가 오래 멈추면 **미래 세션이 바닥난다.**
그러면 "오늘 세션 없음 = 휴장일" 이 거짓이 되어 감시가 조용해진다. 그래서 따로 본다.

- 오늘 이후 세션이 **하나도 없으면** `calendar` 알림을 보낸다 (시장별)
- 이 알림은 휴장일 여부와 무관하다. 달력이 비었다는 사실 자체가 문제다

**바닥나기 전에도 알린다** (2026-09-22, docs/infra.md 25.104).

`calendar` 는 **이미 멈춘 뒤**에 울린다. 달력이 빈 날은 `/api/cron/intraday` 가
"세션 정보 없음" 으로 끝나는 날이고, 그날은 장중 감시가 이미 안 돈 날이다.
달력은 하루에 한 거래일씩 마르므로 **미리 알 수 있는데 그 여유를 하루도 안 썼다.**

- 오늘 이후 세션이 `CALENDAR_LOW_SESSIONS`(=3) **이하**로 남으면 `calendar-low` 를 보낸다
- 종류가 `calendar` 와 **달라야 한다.** 같은 (대상, 시장, 날짜) 라서, 하나였다면
  미리 보낸 `[주의]` 가 UNIQUE 에 걸려 정작 멈춘 날의 `[무응답]` 을 삼킨다
- 문턱 3의 근거는 **실측**이다. 일일 배치는 14일치(`monitor_targets.SESSION_DAYS`)를
  채우고, 2024~2026 의 모든 날을 시작점으로 세면 그 창이 덮는 거래일은
  **국내 5~11일·미국 8~11일**이다(국내 5는 2025-09-27 추석, 미국 8은 2024-12-21 연말).
  배치가 도는 날 아침의 잔량은 최악에도 5이므로 3은 **정상 운영에서 절대 안 울리고**,
  울렸을 때는 아직 세 거래일이 남아 있다

## 3. 알림 규칙

- 같은 (대상, 날짜, 종류) 는 **하루 한 번만** 보낸다. `health_alerts` 의 UNIQUE 가 막는다.
  1시간마다 부르므로 제약이 없으면 하루 열 통이 온다
- 알림에는 **마지막 성공 시각**을 함께 적는다. "얼마나 오래 멈췄나" 가 판단에 필요하다
- 보내기에 실패해도 행은 남기고 `sent_at` 을 비워 둔다. 다음 호출이 다시 보낸다
- 알림 문구는 저장된 값으로만 만든다. 없는 숫자를 지어내지 않는다 (CLAUDE.md 절대 규칙)

문구 예시 (템플릿 + 실제 값):

```
[무응답] 국내 일일 배치가 2026-09-18 09:20 KST 까지 성공 기록이 없습니다.
마지막 성공: 2026-09-17 08:33 (23시간 전)
확인: GitHub Actions → 일일 배치 (국내)
```

## 4. 화면 (`/status`)

들어가는 문은 화면마다 붙는 아래쪽 고지의 "시스템 상태" 링크다. 상단 탭에 넣지
않은 이유는 폰에서 탭이 이미 일곱이고, 이 화면은 무언가 이상할 때만 보기 때문이다.

| 구역 | 무엇 | 출처 |
|---|---|---|
| 무응답 감시 | 대상별 오늘 마감·성공 여부·마지막 성공·최근 알림, 마지막 감시 시각 | `market_sessions` · `batch_runs` · `health_alerts` |
| 최근 배치 | 최근 25건의 상태·시작·끝·지연·단계별 로그(펼침) | `batch_runs` |
| API 한도 | (API·창)마다 가장 새 창 하나. 호출 수 / 한도, 80% 이상 경고색, 100% 또는 저장된 `blocked` 면 차단색. 지금 창(오늘 UTC·이번 달)이 아니면 회색 "지난 창" (25.593) | `api_usage` |
| 데이터 신선도 | 시세·환율·점수·신호·감성·유니버스의 최신 기준일 | 각 표의 MAX(날짜) |
| 크론 호출 | 장중·뉴스 경로를 크론이 실제로 부르고 있나 | `cron_heartbeats` |
| ~~수동 실행~~ (2026-09-17, **2026-10-02 화면에서 뺐다 — 사용자 지시, infra 25.879**) | 13개 작업(일일 배치 국내·미국, 점수, 신호, 성과 지표, 유니버스, 포트폴리오, 신호 성적표, 미국 수정주가 재수집, 실적 일정 추정, 미국 공시, 국내 뉴스 감성 채점(25.595), Turso 로 돌아가기)을 `repository_dispatch` 로 깨운다 (`web/lib/dispatch.ts`, `POST /api/status/run`). 일일 배치는 `client_payload.force` 를 실어 예약 시각 밖에서도 돈다. 도는 배치(`running` 행)와 **요청한 뒤 15분**은 단추가 잠긴다(25.593 — 러너가 기록을 열기 전에 한 번 더 누르면 두 번 돌았다). 페이지를 새로 열면 요청 잠금은 풀린다 | GitHub API |

무응답 감시 표의 **예약** 열은 워크플로 cron 을 사람이 읽는 글로 옮긴 것이다(`WATCHES[].schedule`).
정의처는 워크플로이고, 둘이 어긋나지 않게 테스트가 대조한다(`web/__tests__/dispatch.test.ts`).

화면은 계산하지 않는다. 지연(초)과 비율(%)만 저장된 값에서 나눈다.

**"아직 없음" 과 "못 읽음" 을 가린다** (2026-09-23, docs/infra.md 25.163). 경로가
`read_errors` 를 함께 주고, 구역마다 그것을 먼저 본다. 이 화면이 "크론이 부르고 있나" 를
답하는 자리라, 못 읽고 "호출 기록 없음" 이라 적으면 **사람이 멀쩡한 크론을 다시 등록하러
간다.** 거래일 달력(`market_sessions`)을 못 읽으면 모든 대상이 "거래일 아님" 이 되어
**쉬는 날처럼 보이므로**, 그때는 "늦음 판정을 믿지 마세요" 를 위에 띄운다.

**Actions 사용량은 넣지 않았다.** GitHub 사용량 API 는 계정 단위 권한(admin)을 요구해서
지금 토큰으로는 읽을 수 없다 `[확인필요: fine-grained 토큰으로 읽을 방법]`. 대신 화면에
GitHub 사용량 페이지 링크를 둔다. 월 2,000분 한도는 CLAUDE.md 비용 규칙의 것이다.

## 5. 하지 않는 것

- **자동 재실행.** 멈춘 배치를 감시가 대신 깨우지 않는다. 왜 멈췄는지 모르는 채
  다시 돌리면 같은 실패를 반복하거나 한도를 태운다. 사람이 보고 결정한다 — 그래서
  ~~수동 실행 단추(4장)~~ 는 2026-10-02 화면에서 뺐다(25.879)
- **감시의 감시.** cron-job.org 가 죽으면 감시도 죽는다(1장). 이중화는 무료 범위에서
  방법이 확인되면 그때 한다
- **모든 배치 감시.** 주간·월간 배치(유니버스·재무·ETF 등)는 며칠 밀려도 그날의
  판단을 망치지 않는다. 화면에서는 보이되 알림은 보내지 않는다

## 7. 주간 운영 요약 (2026-10-04, docs/infra.md 25.943)

무응답 감시가 "오늘 안 돈 것" 을 그날 알린다면, 이것은 **"지난주에 무슨 일이 있었나"** 를 일요일 07:41 KST 에 텔레그램 한 통으로 모아 말한다
(`weekly-summary.yml` → `batch/jobs/weekly_summary.py`). 전에는 세션이 `batch_runs` 를 손으로 훑어 확인하던 것들이다.

| 절 | 무엇 | 어디서 |
|---|---|---|
| 실행 | 작업마다 성공·부분·실패·건너뜀 수. 전부 성공이면 한 줄 | `batch_runs` 지난 7일 |
| 되풀이된 경고 | 같은 머리말(24자)의 경고·실패 사유를 묶어 2회 이상만, 많은 순 | `step_log.warnings`·`error_text` |
| Turso 월 읽기 | 쓴 몫과 달의 진도. 진도보다 5%p 넘게 앞서면 ⚠ | `api_usage` (`db.remaining_read_budget_or_none`) |
| 수정주가 | 국내 일일 배치가 "기업행위로 보이는 종목" 을 알린 뒤 `adjust_kr` 성공이 없으면 그 종목들 | `daily_kr` 경고 ↔ `adjust_kr` 실행 |
| 오래 안 돈 예약 작업 | 기대 주기(`EXPECTED_DAYS`)를 넘긴 작업. 한 번도 돈 적이 없으면 그렇다고 | 작업별 마지막 실행 — **성공·부분 성공**(부분도 돈 것이다; 실패·건너뜀은 아니다) |
| **데이터 열 점검** (2026-10-04, infra 25.948) | 행은 들어오는데 **값이 비어 가거나 멈춘** 열. 이상이 없어도 "점검했다" 한 줄은 남긴다 | `services/column_rot` — 표마다 질의 하나(CTE) |

### 7.2 무거운 읽기 기록 — 어느 경로가 월 예산을 쓰나 (2026-10-05, docs/infra.md 25.956)

Turso 월 읽기 카운터(`api_usage.turso_reads`)는 **합만** 안다. 2026-10-05 05:00 UTC 기준 10월 누적 1억 1,800만 행 가운데 배치 작업(`batch_runs.step_log.db_rows_read` 합)은
1,100만 행뿐이었다 — 나머지 1억 700만 행은 웹(Vercel 경로·장중 크론)이고 어느 질의인지 알 길이 없었다. 백테스트 손 실행이 진도 문(25.886)에 걸려 `skipped` 된 것이
이 때문이다. 그래서 웹 DB 층(`lib/db.ts` `tursoBatch`)이 **한 왕복이 20만 행 넘게 훑으면** `health_alerts` 에 한 행을 남긴다(`lib/webUsage.noteHeavyRead`):

```
job = web_heavy_read · market = ALL · local_date = UTC 날짜 · kind = 질의 모양(공백 정리, 앞 60자)
message = "무거운 읽기 7,000,000행 — app/api/recommend/route · SELECT …"
data = {rows, count, route, sql(앞 300자)} — 같은 날 같은 모양이면 count·rows 를 더한다(json_set). 인자 값은 남기지 않는다
sent_at 을 처음부터 채운다 → 텔레그램 무응답 알림으로는 나가지 않는다. /status "최근 알림" 과 DB 에서 읽는다
```

- 문턱 20만 행: 시세 표 전체(약 700만 행)의 3%. 정상 화면 질의는 수천~수만 행이다 `[확인필요: 며칠 기록을 보고 문턱·출처를 적는다]`
- 기록은 곁다리다 — 실패해도 본 질의 결과는 그대로 돌려주고, 기록 중의 기록은 하지 않는다. 기록 자체는 쓰기 1행, 읽기 0 행

### 7.1 데이터 열 점검 — 조용히 썩는 열

신선도는 "행이 들어오나" 를 본다. 행은 매일 들어오는데 그 안의 값이 비어 가거나(미국 재무 열 하나만 null 로 쌓임, 거래대금이 어느 날부터 안 옴)
같은 값으로 굳는(수정주가가 종가와 같은 값으로 되풀이) 고장은 행 수로 보이지 않는다. 그래서 열마다 **최근 7일을 그 전 90일과 견준다** — 절대 문턱이
아니라 **자기 과거와의 차이**다. 미국 시세의 거래대금은 원래 비어 있어(yfinance 가 주지 않는다) 비율이 늘 높은데, 변화만 보니 조용하다.

```
최근  = 날짜 열 >= 오늘−7일          기준 = 오늘−97일 ≤ 날짜 열 < 오늘−7일
빈 값 비율   = NULL 행 / 행           →  최근 − 기준 > 0.20 (20%p) 이면 "비어 갑니다"
고유값 비율  = DISTINCT / 비지 않은 행 →  최근 < 기준 × 0.5 (절반) 이면 "같은 값이 되풀이됩니다"
최근 창의 비지 않은 행이 50개 아래면 판단하지 않는다(고유값 검사, 종목 몇 개의 우연). 빈 값 검사는 최근 행 전체가 50개 아래일 때만 건너뛴다
  — 열이 통째로 비면 비지 않은 행이 0개라 예전에는 놓쳤다(2026-10-06, docs/infra.md 25.976). 기준 창에 행이 없어도 판단하지 않는다
최근 창에 행이 없으면 표마다 한 줄 "최근 7일 행 없음" — 신선도의 일이라 열마다 적지 않는다
```

- 보는 열(`column_rot.WATCHED`): prices(close·adj_close·volume·value) · scores(total_score·sentiment_score) · sentiment_scores(sentiment) ·
  performance_metrics(sharpe·beta) · signals(suggested_amount) · fx_rates(rate) — 열한 열. 바깥에서 받는 값과 계산해 쌓는 값 둘 다
- 읽기: 표마다 질의 하나, 주 1회 20만 행 남짓 — 월 예산의 0.05%. 한 표가 실패해도 나머지는 보고 "(못 본 표: …)" 로 적는다
- `batch_runs.step_log.rot`(발견 글)·`rot_checked`·`rot_errors` 에 남는다. 문턱 20%p·절반·50행은 **추정**이다
  `[확인필요: 몇 주 치 요약에서 오탐·누락을 보고 조정 — 전부 조용하면 문턱이 큰 것일 수 있다]`

- 읽기만 한다. 쓰는 것은 자기 실행 기록 한 줄이다. 조용시간을 보지 않는다(일요일 아침 한 통이라 의미 없다)
- 한 조각(3,900자)에 들어가게 절마다 8줄까지만 싣는다
- 기대 주기 표는 워크플로 cron 보다 넉넉하다(거래일 작업 4일, 주 1회 10일, 월 1회 40일). 설 연휴처럼 11일 쉬면 거래일 작업이 오탐으로 실릴 수 있다 — 알고 둔다
- `/status` 신선도 "주간 운영 요약(마지막 발송)" 칸이 이 요약 자체가 안 온 것을 보인다
