# DB 백업과 복구 (Step 18)

> 2026-09-17 작성. 코드는 `scripts/backup_db.py`, 워크플로는 `.github/workflows/backup.yml`.

---

## 0. 왜 필요한가

Turso 무료 플랜에는 **자동 백업이 없다.** 그리고 이 DB 에는 두 종류가 섞여 있다.

| | 예 | 잃으면 |
|---|---|---|
| **다시 만들 수 없는 것** | 매매·배당 입력, 설정, 시점 재무 스냅샷, 지나간 뉴스·감성 | 끝이다. 어디에도 없다 |
| 다시 받을 수 있는 것 | 시세, 종목마스터, 점수·신호·백테스트 | 시간이 든다. 국내 3년 백필은 하루가 걸렸다(docs/infra.md 15절) |

그래서 두 층으로 나눈다. 필수는 자주·오래, 전체는 가끔·짧게.

## 1. 무엇을 언제 받나

| 층 | 무엇 | 언제 | 보관 |
|---|---|---|---|
| `essential` | 다시 만들 수 없는 표만 (아래) | 매주 월 01:13 KST | 90일 |
| `full` | 모든 표 | 매월 2일·9일 01:47 KST (9일은 예비, infra 25.872) | 30일 |

`essential` 에 드는 표와 이유는 `scripts/backup_db.py` 의 `ESSENTIAL_TABLES` 주석에 있다.
요약하면 **사람이 넣은 것**(`trades` `dividend_receipts` `watchlist` `settings`
`screener_presets` `stock_aliases`),
**지나간 시점이라 되받을 수 없는 것**(`financial_snapshots` `news` `article_sentiments`
`sentiment_scores` `universe_members`), **운영 이력**(`batch_runs` `alerts` `health_alerts`),
그리고 스키마 버전(`schema_migrations`).

> **2026-09-22**: `screener_presets` 가 빠져 있었다(docs/infra.md 25.118).
> `scripts/move_user_data.py` 는 그것을 "사람 손이 닿아 다른 DB 로 옮겨야 하는 것" 으로
> 치는데 백업은 안 담았다 — **같은 뜻을 두 목록이 다르게 알고 있었다.**
> 이제 `tests/test_backup.py` 가 둘을 대조한다.

**`settings` 는 줄 단위로 거른다** (2026-09-23, docs/infra.md 25.155). 대부분 사용자
값이지만 몇 줄은 **지금 이 DB 가 어떤 상태인지**를 적는 운영 표시다 — 복귀 표시
(`db_return_done_at`)·복귀 요청 기록·로그인 잠금 알림 표시. 담았다가 되살리면 **옛 운영
상태가 새 DB 에 심긴다.** 가장 나쁜 것은 복귀 표시다: `auto` 백엔드 판정이 그 한 줄로
Turso 냐 D1 이냐를 고른다(25.12). 목록과 사유는 `backup_db.설정_제외_사유` 에 있고,
이름이 코드와 같은지는 테스트가 대 본다.

**아직 안 담는 것 — 알고 두는 것.** `sell_flags.dismissed_at`("사용자가 확인한 시각")은
사람 입력인데 `sell_flags` 를 담지 않는다. 복원하면 확인해 둔 플래그가 다시 뜬다.
다시 누르면 되는 것이라 크기(보유 × 날짜)를 쓰지 않기로 했다 `[확인필요: 실제 행 수]`.

**안 담는 표에는 사유를 적는다** (2026-09-22, docs/infra.md 25.130).
`scripts/backup_db.백업_제외_사유` 가 그 목록이다. `tests/test_backup_covers_web.py` 가
**웹 소스를 훑어** 웹이 쓰는 모든 표를 찾아내고, 그 표가 `ESSENTIAL_TABLES` 에 있거나
사유가 적혀 있어야 통과시킨다 — 목록끼리 대 보는 것(25.118)으로는 **두 목록에 모두
빠진 새 표**를 못 잡기 때문이다. 사람 손이 닿는 것은 거의 다 웹으로 들어온다.

지금 안 담는 여섯: `api_usage` · `cron_heartbeats` · `login_attempts` ·
`news_fetch_log` · `sell_flags` · `trade_lots`.
`api_usage` 는 `[확인필요]` 가 붙어 있다 — 되살린 날 카운터가 0 에서 시작하므로
그날 D1 하루 쓰기 예산을 실제보다 넉넉히 본다.

보관 기간과 주기는 GitHub 아티팩트 용량을 아끼려고 고른 값이다 `[확인필요: 실제 파일 크기 —
첫 실행 로그에 MB 가 찍힌다. 크면 주기나 보관일을 줄인다]`.

## 2. 어떻게 받나

산출물은 **gzip 으로 압축한 SQL 파일** 하나다. 특별한 도구 없이 `sqlite3` 로 되살릴 수 있다.

> **이 파일은 저장소에 들어가면 안 된다** (2026-09-23, docs/infra.md 25.159).
> 매매 기록·배당·설정·관심 종목과 한국거래소·야후 자료가 통째로 들어 있다.
> `backup/` 과 `*.sql.gz` 는 `.gitignore` 가 막고, `tests/test_gitignore_backup.py` 가
> **git 이 실제로 무시하는지**(`git check-ignore`) 확인한다.
> **압축을 푼 `.sql` 도 막는다** — 아래 3장이 `gunzip` 을 안내하기 때문이다.
> 다만 `migrations/*.sql` 은 예외다(스키마의 단일 정의처). 그러니 되살릴 때 푼 파일은
> `migrations/` 안에 두지 않는다.

```bash
# 손으로 받기 (로컬에 .env 가 있을 때)
python scripts/backup_db.py --scope essential --out backup/

# 클라우드에서: Actions → "DB 백업" → 실행 → 아티팩트 내려받기
```

- **덤프는 읽기만 한다**. `run()` 은 DB 에 아무것도 쓰지 않는다(테스트로 고정)
- **`--record-run` 은 `batch_runs` 에 실행 기록만 남긴다** (2026-09-23, docs/infra.md 25.167).
  자료 표는 건드리지 않는다. 그 전에는 백업이 아무 흔적도 안 남겨 **주 1회가 몇 주째
  멈춰도 알 길이 없었다** — 잃으면 끝인 자료를 지키는 유일한 장치인데.
  기록을 **열기만** 하고, 아티팩트가 올라간 뒤에 워크플로가 `--finish-run <id>` 로
  `success` 로 닫는다. **덤프가 끝난 것과 내려받을 파일이 생긴 것은 다른 일이다** —
  먼저 닫으면 업로드가 실패한 날에도 신선도 칸이 초록이다. 업로드 전에 죽으면 기록은
  `running` 으로 남고 칸은 낡은 채다(맞는 신호다).
  `/status` 의 데이터 신선도 `DB 백업(마지막 성공)` 칸이 그것을 본다
- 큰 표는 2,000행씩 나눠 읽는다. 한 번에 읽으면 응답이 지나치게 커진다

## 3. 어떻게 되살리나

```bash
gunzip -c stock-manager-essential-2026-09-17.sql.gz | sqlite3 restored.db
sqlite3 restored.db "SELECT COUNT(*) FROM trades;"
```

운영 DB 로 되돌릴 때는 **새 Turso DB 를 만들어 거기에 넣고 주소를 바꾼다.** 쓰고 있는 DB 에
덤프를 그대로 부으면 `DROP TABLE` 이 먼저 돈다 `[확인필요: Turso CLI 없이 HTTP 로 대량 적재하는
가장 빠른 방법]`.

**종목 번호를 먼저 대 본다** (2026-09-29, infra 25.676·25.677). 필수 백업에는 종목 마스터가 없어 종목 번호를 가진 표
(매매·배당·관심종목·재무 스냅샷·뉴스 …)의 번호가 원본 그대로다. 백업 머리의 `-- stock_key 번호 종목코드 시장 나라 통화`
대응표(전 종목)로 `restore_backup.py` 가 대상 DB 를 대 본다.
- 대상에 그 번호가 없고 그 종목도 없으면 **같은 번호로 종목 자리**를 만든다 — 빈 새 DB 에 되살린 뒤 마스터를 받으면
  (코드, 시장)으로 그 자리에 덮여 번호가 이어진다. 그래서 **빈 새 DB 에 먼저 되살리고, 종목 마스터는 그 뒤에 받는다**(infra 25.3)
- 같은 번호가 다른 종목이거나 같은 종목이 다른 번호면 **넣지 않는다** — 마스터를 먼저 받은 DB 다
- 대응표 줄이 없는 옛 **전체** 백업은 파일의 종목 행(번호·코드·시장)으로 대응표를 만들어 대조한다 (25.683)
- 같은 번호·같은 코드인데 시장만 다르면(거래소 이전) 어긋남이 아니다
- 파일에 종목 행이 있어도(전체 백업) 종목 번호 대조를 한다. 대상 DB 에 이미 마스터가 있으면 파일의 종목 행은
  INSERT OR IGNORE 로 무시되기 때문이다. 대상에 없는 번호는 파일의 **실제 종목 행**으로 채우고, 파일에도 없으면
  이름 없는 자리를 만든다. 이 채움은 `--max-rows` 예산을 쓰지 않는다 (docs/infra.md 25.681)
- 대응표가 없는 옛 백업만 `--trust-stock-ids`(워크플로 `trust_stock_ids`)를 켜야 넣는다 — 원본과 종목 번호가 같은 DB 일 때만.
  대응표가 있으면 켜도 무시한다(25.679)

되살린 뒤에는 **마이그레이션을 한 번 돌린다**(`migrate.yml`). 백업 시점 이후에 생긴 표가 있으면
그때 만들어진다. `schema_migrations` 를 함께 받는 이유가 이것이다 — 어디까지 적용된 상태인지 알아야 한다.

## 6. 복구 리허설 (2026-10-04, docs/infra.md 25.946)

**백업은 복구해 봐야 백업이다.** 덤프는 매주 돌고 기록도 남지만(25.167), 그 파일로 실제로 되살려 본 적이 운영 기록에 없었다.
`restore-drill.yml` 이 **분기마다**(1·4·7·10월 5일) 가장 최근 필수 백업 아티팩트를 받아 `scripts/restore_drill.py` 로 돌린다. 수동으로도 돌린다(전체 백업도 고를 수 있다).

- 빈 SQLite 파일에 마이그레이션을 적용하고, `restore_backup` 과 **같은 길**(따옴표 셈으로 문장 가르기, 따옴표 밖 표식만 읽기)로 넣는다
- 표마다 `COUNT(*)` 를 백업의 `-- rows <표> <n>` 과 대 본다. 하나라도 어긋나거나 넣다가 오류가 나면 **실패**(종료코드 1). 마이그레이션이 미리 채우는 표(`schema_migrations`·`stock_aliases`)는 "적힌 값 이상" 이면 통과
- **운영 DB 를 건드리지 않는다.** `batch_runs` 에 결과 한 줄(job `restore_drill`)만 적어 `/status` 신선도 "백업 복구 리허설" 칸이 마지막 리허설을 보인다. 결과 본문은 이슈 #1 에도 남는다
- 행 수 표식이 없는 옛 백업은 "대조할 수 없다" 로 실패한다 — 그런 백업은 보관 기간이 지나 곧 사라진다

리허설이 실패하면 다음 백업이 돌기 전에 원인을 본다 — 백업 스크립트가 깨진 것인지(최근 커밋), 마이그레이션이 백업 뒤에 열을 바꿨는지(`restore_backup` 은 데이터만 넣으므로 열 수가 다르면 INSERT 가 깨진다).

## 4. 하지 않는 것

- **자동 복구.** 되살리기는 사람이 확인하고 한다. 잘못 부으면 원본을 덮는다
- **암호화.** 저장소가 프라이빗이고 아티팩트도 저장소 권한을 따른다. 키를 하나 더 두면
  그 키를 잃었을 때 백업이 통째로 쓸모없어진다 `[확인필요: 외부로 내보낼 때는 다시 판단]`
- **외부 저장소(S3 등)로 보내기.** 무료 조건과 카드 등록 여부를 확인하지 않았다(CLAUDE.md 비용 규칙)
